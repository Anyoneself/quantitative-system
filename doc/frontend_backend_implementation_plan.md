# 量化系统前后端与部署实施计划

> 文档状态：历史实施计划。白色前端、SQLite 7 表、组合流水与净值、风险指标、模型验证、回测页面和 Docker/Compose 已完成首轮落地；当前实际模块、API 和数据库以 `doc/quantitative_system_architecture.md` 为准。本文后续章节中的“建议”“计划”和扩展表仍表示原始路线图，不代表已经实现。
>
> 最终发布边界：交易写入使用同一组合内唯一的 `request_id` 保证幂等；组合估值只使用 `adjustment_type = "NONE"` 的未复权行情；交易日期必须存在于已保存并通过质量校验的未复权日线；净值落后于当前账本时风险状态为 `STALE`，没有可用净值时为 `NO_DATA`；单项金额或价格上限为 `10^12` 元、数量上限为 `10^9` 股，成交金额换算为整数分后还必须处于 SQLite 安全整数范围内。

## 1. 文档目的

本文档用于指导量化系统从当前的本地分析工具，逐步升级为具有白色可视化仪表盘、数据持久化、组合分析、风险监控和容器化部署能力的完整应用。

实施遵循以下原则：

- 复用现有行情、分析、扫描和回测代码。
- 优先完成最小可用闭环，不提前建设实盘交易能力。
- 第一版使用单机同步架构，不引入微服务、消息队列或分布式调度。
- 所有界面指标必须来自真实接口或明确的测试样例，不硬编码虚假业务数据。
- 每个阶段必须有可执行测试和明确验收条件。

## 2. 立项时项目基线（历史）

当前仓库已经具备以下能力：

- 使用免登录公开接口获取 A 股日线、股票列表和资金流数据。
- 计算技术指标、量价形态、机器学习概率、资金流和背驰信号。
- 生成单股买入观察建议和持仓卖出风险建议。
- 执行股票池扫描、全 A 扫描和单股回测。
- 提供 CLI、本地 HTTP 服务、JSON API 和 SSE 扫描进度。
- 提供原生 HTML、CSS、JavaScript 前端。

立项时主要缺口：

- 前端为深色单股分析界面，与目标白色仪表盘不一致。
- 没有数据库，行情、交易、持仓、回测和净值结果无法持久化。
- 没有投资组合、资产配置和组合净值计算。
- 没有统一的收益与风险指标服务。
- 没有仪表盘聚合接口。
- 没有 Dockerfile、Compose、健康检查和数据卷配置。
- `src/web.py` 同时承担路由、参数处理和响应构造，继续扩展后职责会过重。

## 3. 建设目标

目标系统形成以下业务闭环：

```text
公开行情采集
  -> 原始数据落盘
  -> 清洗与质量检查
  -> 策略分析和回测
  -> 组合与交易记录
  -> 收益和风险计算
  -> REST API
  -> 白色仪表盘前端
  -> Docker 镜像部署
```

保留现有能力：

- 单股买入分析。
- 持仓卖出判断。
- 全 A 扫描。
- 资金流和背驰分析。
- 单股回测。
- CLI 命令。

新增能力：

- 量化投资总览。
- 组合净值与基准对比。
- 策略表现列表。
- 资产配置展示。
- 组合风险指标。
- 手工维护投资组合和交易流水。
- 行情、业务记录和计算结果持久化。
- Docker 一键构建和启动。

第一版明确不包含：

- 券商账户连接。
- 自动下单或实盘交易。
- 多用户权限系统。
- 分布式扫描。
- 高频行情和盘中撮合。
- 云端托管数据库。

## 4. 总体架构

### 4.1 逻辑架构

```text
浏览器
  -> 静态前端
  -> REST API / SSE
  -> 应用服务
       -> 仪表盘聚合
       -> 组合与持仓
       -> 收益和风险

```

### 4.2 后端方案

后端继续使用 Python，复用：

- `src/data/`
- `src/analysis/`
- `src/backtest/`
- `src/web.py`

- Python 3.11。
- SQLite。
- 标准库 `sqlite3`。

## 5. 数据存储设计

### 5.1 存储边界

默认数据目录：

```text

├── app/
│   └── quantitative_system.db
├── raw/
│   ├── kline/
│   ├── fund_flow/
│   └── stock_list/
```

存储规则：

- 数据库保存标准化行情、业务记录和计算结果。
- 公开接口原始响应先写入 `data/raw/`，再进行解析和标准化。
- 导出的 CSV 和 JSON 保存到 `data/export/`。
- `data/` 默认不提交到 Git。
- 小型稳定测试样例放入 `tests/fixtures/`。
- 敏感信息不得写入数据库迁移、镜像或版本库。

## 6. 业务指标口径

所有前端指标由后端统一计算。

### 6.1 收益指标

- 总资产：现金加持仓按最新有效收盘价计算的市值。
- 今日收益：最新交易日总资产减上一交易日总资产，并扣除当日资金调整影响。
- 累计收益率：当前净值相对初始净值的变化率。
- 年化收益率：根据实际净值区间按交易日数量折算。
- 策略净值：组合每日总资产除以初始资金。
- 基准净值：基准收盘价相对组合起始日收盘价归一化。

### 6.2 风险指标

- 年化波动率：日收益率标准差乘以 `sqrt(252)`。
- 夏普比率：年化超额收益除以年化波动率。
- Beta：组合日收益与基准日收益的协方差除以基准日收益方差。
- VaR(95%)：第一版使用历史模拟法。
- 最大回撤：净值相对历史峰值的最大跌幅。
- 胜率：已平仓交易中盈利交易数量占比。
- 盈亏比：平均盈利金额除以平均亏损金额绝对值。

第一版无风险利率默认为 `0`，并允许通过配置修改。

样本不足、基准缺失或分母为零时返回 `null` 和原因，禁止以 `0` 伪装有效指标。

### 6.3 风控状态

第一版风险等级：

- `NORMAL`：所有指标处于阈值内。
- `WARNING`：至少一个指标超过预警阈值。
- `HIGH`：至少一个指标超过高风险阈值。
- `NO_DATA`：有效样本不足。

阈值的业务含义必须使用中文注释说明，并集中配置，不散落在前端或多个模块中。

## 7. 前端页面计划

### 7.1 量化投资总览

对应目标效果图的核心内容：

- 总资产。
- 今日收益。
- 累计收益率。
- 最大回撤。
- 策略净值与沪深 300 对比。
- `1月`、`3月`、`今年`、`1年`时间范围切换。
- 风险雷达图和指标明细。
- 策略表现表。
- 资产配置环形图。
- 风控状态。
- 数据更新时间和市场状态。

### 7.2 行情中心

迁移并保留现有能力：

- 股票代码搜索。
- 价格和成交量图。
- 技术指标。
- 资金流。
- 背驰信号。
- 全 A 扫描。

### 7.3 策略研究

第一版只展示已有策略和真实参数：

- 策略名称。
- 启用状态。
- 当前参数。
- 最近分析或回测时间。
- 关联回测结果。

### 7.4 回测分析

- 创建回测。
- 查看运行状态。
- 查看收益和风险摘要。
- 查看净值和回撤曲线。
- 查看交易记录。
- 导出 JSON 或 CSV。

### 7.5 组合管理

- 新建投资组合。
- 设置初始资金和比较基准。
- 录入买入、卖出、分红和资金调整。
- 查看持仓数量、成本、市值、浮动盈亏和仓位占比。
- 删除交易前进行二次确认。

### 7.6 风险监控

- 查看当前风险等级。
- 查看指标阈值和触发原因。
- 查看历史风险快照。
- 定位引起风险变化的持仓或净值变化。

## 9. Docker 与镜像计划

新增文件：

```text
Dockerfile
docker-compose.yml
.dockerignore
config/runtime.example.env
scripts/docker-entrypoint.sh
```

### 9.1 镜像要求

- 使用 Python 3.11 slim 基础镜像。
- 使用多阶段构建。
- 使用非 root 用户运行。
- 只安装生产运行所需内容。
- 不把本地数据库、行情数据和敏感配置复制进镜像。
- 默认监听 `0.0.0.0:8000`。
- 支持容器优雅退出。
- 使用 `/api/health` 进行健康检查。
- 镜像内使用固定工作目录。

### 9.2 Compose 要求

- 暴露 Web 端口。
- 将宿主机数据目录挂载为持久卷。
- 从环境变量文件读取非敏感配置。
- 设置合理的重启策略。
- 配置健康检查。

预期启动命令：

```bash
docker compose up -d --build
```

预期停止命令：

```bash
docker compose down
```

停止容器不得删除数据卷。清理数据卷必须由使用者明确执行。

### 9.3 第一版容器边界

第一版仅使用一个应用容器和一个持久数据卷，不引入：

- PostgreSQL。
- Redis。
- Nginx。
- Celery。
- Kubernetes。

当出现多用户并发、远程部署或大规模历史数据后，再单独评估数据库和任务调度升级。

### 10.2 数据库测试

### 10.6 前端检查

## 14. 主要风险与应对

### 公开数据源不稳定

应对措施：

- 保留现有超时、限速、有限重试和备用来源。
- 原始响应落盘。
- 数据刷新失败返回明确状态。
- 仪表盘展示最近一次成功更新时间。

### 指标口径不一致

应对措施：

- 所有指标由后端统一计算。
- 前端只负责格式化和展示。
- 为每个核心指标提供固定样例测试。

### SQLite 并发写入限制

应对措施：

- 第一版控制为单机单进程。
- 写操作使用短事务。
- 开启外键约束和合理的忙等待。
- 出现明确多用户并发需求后再评估 PostgreSQL。

### 视觉页面先于真实数据

应对措施：

- 先定义 API 契约和数据口径。
- 使用明确标识的测试样例开发。
- 验收时禁止页面保留硬编码业务数字。

### 功能范围持续扩大

应对措施：

- 第一里程碑只交付仪表盘最小闭环。
- 菜单页面随真实功能逐项开放。
- 实盘交易、多用户和分布式能力单独立项。
